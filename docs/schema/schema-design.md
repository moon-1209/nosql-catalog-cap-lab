# Chebotko Schema Design - A vs B

Chebotko-notation diagrams of the two candidate layouts for the catalog
workload. Diagrams are generated by `scripts/render_chebotko.py`
(deterministic; re-run it after any key change).

- [Schema A diagram](chebotko/schema-a.svg)
- [Schema B diagram](chebotko/schema-b.svg)

Notation: **K** = partition-key column, **C v / C ^** = clustering column
with descending / ascending order, plain columns below the separator are
payload. Arrows show which access patterns (from
`docs/access-patterns/access-patterns.md`) each table serves.

## Shared lookup table

Both schemas keep `products_by_id` (`PRIMARY KEY (product_id)`) so Q1
point lookups and writes that only know the product id stay O(1) without
`ALLOW FILTERING`. Writers update both tables in one batch.

## Schema A - `products_by_category`

`PRIMARY KEY ((category_id), added_at, product_id)`
`CLUSTERING ORDER BY (added_at DESC, product_id ASC)`

- **Partition key**: `category_id` alone - all products of a category
  share one CQL partition, one token range, one replica set.
- **Data distribution**: partition size = category size; load skew equals
  category-traffic skew. Under a Zipf workload the hottest partition can
  exceed the mean by an order of magnitude.
- **Reads**: Q2/Q3/Q4 are single-partition reads - cheapest possible
  per request, all pressure lands on one node group.

## Schema B - `products_bucketed`

`PRIMARY KEY ((category_id, bucket), added_at, product_id)`
same clustering order; `bucket = hash(product_id) % NUM_BUCKETS`
(`NUM_BUCKETS = 16` in `src/catalog_analysis/schemas.py`).

- **Partition key**: composite `(category_id, bucket)` - a category is
  split into 16 partitions spread across the token ring.
- **Data distribution**: max partition load ~ category load / 16, bounded
  independently of category popularity.
- **Reads**: Q2/Q3/Q4 fan out to all 16 buckets
  (`bucket IN (0..15)`); the app merges and re-sorts by `added_at`.
  More coordinator work and higher tail latency per request.
- **Writes**: unchanged cost - `bucket` is derived client-side, so each
  write still hits exactly one partition.

## Comparison

| Aspect | Schema A | Schema B |
|--------|----------|----------|
| Partition key | `(category_id)` | `(category_id, bucket)` |
| Partitions per category | 1 | `NUM_BUCKETS` (16) |
| Max partition size (500k products, 20 cats, Zipf a=1.2) | ~ 1 hot partition can hold >20% of all rows | ~ category size / 16 |
| Category read (Q2-Q4) partitions touched | 1 | 16 (fan-out + merge) |
| Point lookup Q1 | `products_by_id` (identical) | `products_by_id` (identical) |
| Write amplification | 2 tables | 2 tables |
| Coordinator / merge cost | None | App merges 16 sorted pages |
| Hot-partition exposure | **High** under skewed traffic | Low - bounded by bucket count |
| Data modelling trade-off | read-optimised | distribution-optimised |

Neither schema changes the business model: identical payload columns,
identical clustering order; only partition granularity differs. The
benchmark (hot-partition charts + stale-read analysis) decides whether
B's fan-out cost is worth A's hotspot removal.
